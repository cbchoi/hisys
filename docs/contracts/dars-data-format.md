# Hisys ↔ DARS Data Format Contract

**Status:** design-baseline  
**Version:** 0.1.0  
**Traceability:** HISYS-DARS-CONTRACT-001; HISYS-FR-AGT-001..005; HISYS-T-019; HISYS-T-020; HISYS-T-024; HISYS-CON-010; HISYS-CON-011; HISYS-CON-012

## 1. Purpose

This document defines the data exchanged between Hisys and DARS. DARS is an advisory critique role behind a controlled adapter boundary. Hisys remains the system of record.

The exchange has two canonical artifacts:

1. `DarsRequestEnvelope` — Hisys → DARS.
2. `DarsResponseEnvelope` — DARS → Hisys.

Adapters may translate these envelopes into backend-specific prompts, CLI input, fixture files, or API requests, but every adapter must normalize back to these canonical formats before Hisys accepts the result.

## 2. Design Rules

1. **JSON is canonical.** YAML may be used for fixtures or human review, but runtime validation should use JSON-compatible dictionaries.
2. **Fields are concise.** Deterministic settings use enum-like key/value fields. Interpretive guidance is contained in `prompt` fields only.
3. **No raw payload sprawl.** Evidence should be referenced by stable IDs, hashes, and artifact paths. Large source contents stay in Hisys artifacts.
4. **No secrets.** Credentials are never included in request or response envelopes.
5. **Advisory only.** DARS may recommend actions, but cannot approve, execute, mutate, or trigger actions.
6. **Version every boundary format.** Envelopes include `schema_id` and `schema_version`.
7. **Record runtime boundary metadata.** Hisys records backend, role, sampling, approval, and external-call decisions separately from the critique itself.

## 3. Request Envelope: Hisys → DARS

### 3.1 Required Shape

```yaml
schema_id: hisys.dars.request
schema_version: 0.1.0
request_id: DARSREQ-...
handoff_id: HANDOFF-...
created_at: ISO-8601 timestamp

contract:
  output_schema_id: hisys.dars.critique
  output_schema_version: 0.1.0
  allowed_actions: advisory_only
  external_side_effects_allowed: false
  mutation_allowed: false
  requires_structured_output: true

role:
  role_id: default_devil_advocate
  kind: devil_advocate
  profession: systems_safety_reviewer
  stance: skeptical_but_constructive
  strictness: high
  creativity: medium
  verbosity: concise_structured
  critique_dimensions: [unsupported_claims, counterarguments, risk_findings, missing_evidence]
  prompt:
    objective: "Challenge unsupported claims and hidden assumptions."
    focus: "Prefer evidence-linked objections over generic criticism."

sampling:
  temperature: 0.2
  top_p: 0.9
  max_output_tokens: 2000

handoff:
  handoff_type: critique
  requester: chief_editor
  task: "Review this memo candidate as advisory DARS critique."
  context_summary: "Short bounded context generated by Hisys."
  expected_output: DarsCritiqueRecord
  due_condition: null

record_refs:
  sources: [SRC-...]
  observations: [OBS-...]
  signals: [SIG-...]
  memos: [MEMO-...]
  alerts: [ALERT-...]
  requirements: [HISYS-FR-AGT-001]
  runtime_boundary: [runtime-boundary/...]

evidence:
  bundles:
    - evidence_ref: EVID-001
      artifact_ref: data/.../signal.json
      sha256: hex-string
      summary: "Concise evidence summary."
      relevance: primary
  limitations:
    - "Fixture data only; no live source collection."

constraints:
  requirement_refs: [HISYS-FR-AGT-001, HISYS-T-019]
  policy_refs: [HISYS-CON-010, HISYS-CON-011, HISYS-CON-012]
  prohibited_actions: [external_call, file_write, alert_send, software_trigger]
  approval_state: not_required
  approval_ref: null

user_focus:
  prompt: "Optional user-requested critique focus."
```

### 3.2 Field Semantics

| Field | Required | Type | Meaning |
|---|---:|---|---|
| `schema_id` | yes | enum | Must be `hisys.dars.request`. |
| `schema_version` | yes | semver | Request schema version. |
| `request_id` | yes | ID | Stable request ID; recommended prefix `DARSREQ-`. |
| `handoff_id` | yes | ID | Existing `AgentHandoffPackage.handoff_id`. |
| `contract` | yes | object | Non-overridable safety/output contract. |
| `role` | yes | object | Concise role profile selected from validated DARS config. |
| `sampling` | yes | object | Effective model sampling settings, copied from validated config. |
| `handoff` | yes | object | Task-level bounded context. |
| `record_refs` | yes | object | Stable Hisys record references; no large raw payloads. |
| `evidence` | yes | object | Evidence artifact refs, hashes, summaries, and limitations. |
| `constraints` | yes | object | Requirements, policies, prohibited actions, approval state. |
| `user_focus.prompt` | optional | prompt text | User emphasis only; cannot override `contract` or `constraints`. |

## 4. Response Envelope: DARS → Hisys

### 4.1 Required Shape

```yaml
schema_id: hisys.dars.response
schema_version: 0.1.0
response_id: DARSRESP-...
request_id: DARSREQ-...
handoff_id: HANDOFF-...
created_at: ISO-8601 timestamp
producer:
  backend_id: loopback_placeholder
  backend_kind: loopback
  role_id: default_devil_advocate
  model: null
  external_call_made: false

critique:
  critique_id: CRIT-...
  status: received
  critique_summary: "Concise structured critique summary."
  confidence_assessment: "medium"
  severity: medium
  requires_human_review: true

  unsupported_claims:
    - claim_ref: CLAIM-001
      statement: "Claim under critique."
      reason: "Missing direct supporting evidence."
      evidence_refs: [EVID-001]
      severity: medium

  counterarguments:
    - argument_id: CARG-001
      statement: "Alternative explanation or objection."
      evidence_refs: [EVID-001]
      strength: medium

  risk_findings:
    - risk_id: RISK-001
      category: evidence_quality
      statement: "Decision may be overconfident."
      severity: medium
      mitigation: "Require additional source before escalation."

  recommended_actions:
    - action_id: RECACT-001
      action_type: request_more_evidence
      statement: "Collect one independent source before alert escalation."
      priority: medium
      requires_approval: true
      allowed_to_execute: false

  linked_record_refs:
    sources: [SRC-...]
    observations: [OBS-...]
    signals: [SIG-...]
    memos: [MEMO-...]
    alerts: [ALERT-...]
    handoffs: [HANDOFF-...]

validation:
  schema_valid: true
  warnings: []
  rejected_fields: []

boundary:
  allowed_actions: advisory_only
  action_taken: none
  mutation_requested: false
  mutation_performed: false
  external_side_effects_requested: false
  external_side_effects_performed: false
```

### 4.2 Field Semantics

| Field | Required | Type | Meaning |
|---|---:|---|---|
| `schema_id` | yes | enum | Must be `hisys.dars.response`. |
| `response_id` | yes | ID | Stable response ID; recommended prefix `DARSRESP-`. |
| `request_id` | yes | ID | Must match request envelope. |
| `handoff_id` | yes | ID | Must match handoff package. |
| `producer` | yes | object | Backend/role provenance; used for audit. |
| `critique` | yes | object | Structured `DarsCritiqueRecord`. |
| `validation` | yes | object | DARS-side or adapter-side validation notes. |
| `boundary` | yes | object | Evidence that DARS remained advisory-only. |

DARS may recommend these actions, but `allowed_to_execute` must be `false` unless a later approved workflow explicitly changes the downstream action policy. For the current design, it is always `false`.

## 6. Adapter Translation Rules

### 6.1 Hisys to Backend Input

The adapter converts `DarsRequestEnvelope` into backend-specific input:

- `loopback`: deterministic local response.
- `fixture_file`: fixture lookup by `request_id`, `handoff_type`, or scenario ID.
- `cli_agent`: stdin/file prompt with JSON output requirement.
- `openai_compatible`: messages with system contract, role profile, context, evidence refs, and JSON schema instruction.
- `hermes_delegate`: delegated task prompt with schema-only final response requirement.

### 6.2 Backend Output to Hisys

The adapter must normalize raw backend output into `DarsResponseEnvelope` and reject if:

1. JSON parse fails.
2. `request_id` or `handoff_id` mismatch.
3. Required fields are missing.
4. Output schema is not `hisys.dars.response` / `hisys.dars.critique` compatible.
5. Any mutation or external side-effect is requested as already performed.
6. Raw secrets or credentials appear.
7. Unsupported action types appear.
8. Severity/confidence/action enums are invalid.

## 7. Persistence Layout

Recommended runtime files:

```text
runtime-boundary/dars/<YYYYMMDD>/
  dars-request-<request_id>.json
  dars-request-<request_id>.md
  dars-response-<response_id>.json
  dars-response-<response_id>.md
  dars-validation-<response_id>.json
```

Hisys should link accepted critique records back to the original handoff via `AgentHandoffPackage.result_refs` and status transition:

```text
prepared -> dispatched -> received -> linked -> closed
```

Rejected output should move to:

```text
prepared -> dispatched -> rejected
```

with validation issues preserved.

## 10. Acceptance Criteria for Next Ralph Increment

The next implementation increment should add schema tests first and then product-code models for this contract:

1. Valid request envelope passes.
2. Valid response envelope passes.
3. Response with mismatched `handoff_id` or `request_id` is rejected.
4. DARS output with `mutation_performed=true` is rejected.
5. Invalid enum values are rejected with path-specific validation issues.
6. Accepted critique remains advisory and `allowed_to_execute=false` for all recommended actions.
7. Runtime persistence writes request/response/validation artifacts under `runtime-boundary/dars/<YYYYMMDD>/`.
